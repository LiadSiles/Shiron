# Shiron (שירון) — guide for LLM contributors

A song library for a kindergarten teacher (גננת). She forwards songs from WhatsApp — voice
notes, mp3s, YouTube links — and the app stores them, names them, sorts them into
categories, ranks them by use, searches them by lyrics, and plays them with the screen off.
Hebrew-first UI, forced RTL. Owner: Liad. **iPhone is the top-priority platform**; Android
exists so the owner can test on his own phone.

Read `docs/wiki/README.md` before changing anything non-trivial. The wiki holds the facts
that are expensive to rediscover (iOS audio limits, the native audio module, the AI services, decisions
already taken and why).

## Hard constraints — do not "fix" these away

- **iOS first.** Every feature must work on iPhone. Test assumptions against iOS limits in
  `docs/wiki/ios-constraints.md` (e.g. iOS cannot play WhatsApp's Ogg/Opus voice notes).
- **No server of our own.** Audio is converted on the phone (native module); the only network
  calls are to the AI services (Groq, Gemini) with the user's own keys and to YouTube oEmbed.
  The library lives on the phone. Don't add a backend, analytics or any other service without
  the owner's decision — recordings may contain children.
- **AI = cloud models, free tier, Groq or Gemini, each user's own key.** No local models, no
  paid services, no key in the build or the repo. Groq is the recommended default; Gemini's
  free tier may train on what it receives, so it is offered with a plain warning (owner's
  decision, see `decisions.md`). Another service = the owner's decision. Connecting must stay a
  guided in-app flow (`src/app/connect.tsx`). Without a key, songs are still saved and playable.
- **The AI suggests, the teacher decides.** A title or category the teacher set
  (`titleSource = 'user'`, `confirmed = true`) is never overwritten by processing.
- **YouTube: visible embedded player only.** No downloading, no background playback of
  YouTube (Terms of Service). See `decisions.md`.
- **Zero maintenance for the teacher.** The library must work well even if she never
  approves or edits anything. Anything that needs setup is a bug in the design.
- **Playing comes first.** Common song = 2 taps from the home screen. Touch targets ≥ 48 pt.
- **Continuous Native Generation.** `app/ios` and `app/android` are generated by
  `expo prebuild` and git-ignored. Configure native behaviour only in `app/app.json` and
  config plugins (`app/plugins/`). Never hand-edit or commit native folders.

## Build, test, release

```bash
npm run install:all     # app dependencies
npm run check           # typecheck + unit tests
npm run test:ios-audio  # audio module on a Mac (Swift package + fixtures)
npm run version:bump -- minor   # when a roadmap version is reached
```

- CI (`.github/workflows/ci.yml`): typecheck, tests, `expo prebuild` + native-config
  assertions. `native.yml`: the audio module on macOS (Swift package) and an Android emulator,
  against shared fixtures. **CI is the native compile and test check** — this sandbox has no
  Xcode or Android SDK.
- Releases (`.github/workflows/release.yml`): every push to `main` touching the app
  publishes a GitHub Release. A new version → `v<version>` with APK **and** unsigned IPA;
  otherwise `v<version>-build.<n>` prerelease with the APK. Details and gotchas:
  `docs/wiki/build-and-release.md`.
- Read failures through the REST API (`gh api repos/LiadSiles/shiron/actions/runs`, then
  `.../check-runs/<id>/annotations`); raw logs may be unreachable. Workflows re-emit
  compiler errors as `::error::` annotations for that reason.
- Expo SDK 58. Expo changes every SDK: read `app/AGENTS.md` and the versioned docs before
  touching any Expo API; do not trust memory. Add packages with `npx expo install`
  (`EXPO_OFFLINE=1` in this sandbox — the version check endpoint is blocked).

## Working agreements

- **Keep the knowledge current.** When you learn a platform fact, hit a gotcha, or make a
  decision, update the matching wiki page in the same commit (`decisions.md` for decisions,
  `roadmap.md` for status, `build-and-release.md` for CI/tooling gotchas). The owner also
  keeps a Hebrew planning doc in claude.ai ("שירון הגן — תוכנית מוצר ועיצוב"); product-level
  changes are reflected there too.
- UI strings are Hebrew, feminine second person ("נגני", "שמרי") — the teacher is addressed
  directly. Code, comments, commit messages and the wiki are English. User-facing docs
  (README, CHANGELOG, release notes) are Hebrew.
- Layout is RTL. Use `start`/`end`, never `left`/`right`, except for timelines that must read
  left-to-right (progress bar) — mark those with `direction: 'ltr'`.
- Commits: imperative subject, body explains *why*. One logical change per commit.
  User-visible changes get a line under `CHANGELOG.md` → `[Unreleased]`.
- Pure logic goes in `app/src/core/` with a test in `app/tests/`. Anything that touches
  React Native stays out of `core/`.
- The audio algorithm (`LoudnessPlan`) exists in Swift and Kotlin: change both, and both tests.
  A new format = a fixture in `modules/shiron-audio/fixtures/` + its expectation in both tests.
- No dead code: remove what nothing calls (git history keeps it).
- Prefer verifying over assuming: run the code, the tests, or a prebuild; for device-only
  behaviour, say plainly that it is untested on a device.
